# Peri-Alpine ZooScan 2024 — source assessment

> **Verdict: assessed, recorded, *not* a registry source.** The deposit named by
> [issue #13](https://github.com/Inria-Chile/planktonzilla/issues/13) publishes **one table and no
> images**, and it names no EcoTaxa project that the images could be walked from. This file is the
> measured record of what it does hold, of how that was established, and of the single fact that
> would turn it into an importable source. Nothing here downloads or builds anything.

`perialpine_zooscan_2024` is the key this source would take if it ever joins the registry. Unlike
`frepj` or `daplankton`, that name is ours and not upstream's: the deposit carries no acronym.

## 2. What the file holds

Two sheets, no embedded media, and no blank cell anywhere in either data block (both sheets open
with a title row above their header).

**Sheet 1 — the objects.** 11,081 rows: one title row (`Lakes-datapaper-ID`, the reason Dataverse's
ingest names the TSV's first columns `B`…`J`), one header row, and **11,079 objects**, one per
scanned specimen. Ten columns:

| Column | Content |
| --- | --- |
| `object_id` | `<lake_id>_<NN>_<year>_<n>`, e.g. `ANN74_03_2024_565`. Unique across the file (11,079/11,079). EcoTaxa's `orig_id` shape — this is the join key an image fetch would need. |
| `date` | Sampling date, `YYYY-MM-DD`, 12 distinct values |
| `lake`, `lake_id` | `Annecy`/`ANN74`, `Bourget`/`BOU73`, `Geneva`/`LEM74` |
| `annotation` | The validated EcoTaxa label — 20 distinct strings |
| `taxonomy` | That label's full EcoTaxa lineage, `>`-separated, 6 to 12 nodes deep |
| `area_px`, `major_axis_px`, `minor_axis_px` | ZooProcess morphometry of the vignette, in pixels |
| `particle_pixel_size_mm` | `1.06E-2` on every row — 10.6 µm/px, the ZooScan's 2400 dpi scale |

Morphometric spread, over all 11,079 objects: `area_px` 633 – 67,850 (median 3,116);
`major_axis_px` 29.3 – 520.5 (median 84.4), i.e. **0.31 – 5.52 mm** at the stated pixel size;
`minor_axis_px` 14.4 – 259.1 (median 46.1).

**Sheet 2 — "Table 1", the stations.** Three rows, one per lake, with the identifiers and lake
morphometry reproduced in §3.2. It is what makes the objects geolocatable: the file itself carries
no per-object coordinates.

Read that table before assuming 20 classes. It is 20 label *strings* over **19 lineages**:
`nauplii_Copepoda` (156) and `nauplii<Copepoda` (2) resolve to the same
`…>Copepoda>nauplii`, one taxon spelled two ways — see §6.1. Six labels also differ from the last
node of their own lineage, because they use EcoTaxa's qualifier convention with both separators:
`egg_sac<Copepoda`, `part_Copepoda`, `nauplii_Copepoda`, `nauplii<Copepoda`, `egg<Cladocera`,

The class distribution is the long tail this repository is built for: the top three labels
(`Eudiaptomus_gracilis`, `Cyclops_prealpinus`, `Daphnia_sp`) are 69.1% of the file, and seven
labels have 20 objects or fewer — one of them, `Chaoboridae`, has exactly one.

## 4. Why it is not a registry source: there are no images

Every source in `configs/dataset_import/` ends in an imagefolder. This deposit cannot, and the
finding is not an inference from its size — it is what five independent checks say. All were run on
2026-09-18.

1. **The deposit has exactly one file**, the workbook of §1. `GET /api/datasets/:persistentId/`
   lists `files: 1`.
2. **The workbook embeds no media.** A `.xlsx` is a zip; this one holds
   `xl/worksheets/sheet{1,2}.xml`, `sharedStrings.xml`, `styles.xml`, `theme1.xml` and the two
   `docProps` — there is no `xl/media/` entry, which is where an embedded picture would live.
3. **No companion image deposit exists.** The CARRTEL Dataverse holds seven datasets
   (`GET /api/search?subtree=carrtel`); the only other zooplankton one, `French3lakes`
   ([10.57745/VNYZ9A](https://doi.org/10.57745/VNYZ9A)), is community-composition counts — also a
   single tabular file.
4. **No paper names the images.** DataCite records exactly one related identifier for the DOI,
   `HasPart → 10.57745/AHK6AU` (its own file), and no relation to any publication; a Crossref title
   and author search returns no data paper for it.
5. **The abstract points at EcoTaxa but names no project.** It says the data "can be used as a model
   database to train automated identification using the online interface Ecotaxa
   (https://ecotaxa.obs-vlfr.fr)" — the service, not a project. And EcoTaxa will not give the
   project up to an anonymous client: `GET /api/projects/search?title_filter=Annecy&not_granted=true`
   answers `200` with one object per match carrying **only** `instrument` and `instrument_url` — no
   id, no title — with or without a `fields=` projection, and `GET /api/collections/search` answers
   `403 Not authenticated`. The same search hides the ids of the seven Tara Pacific projects this
   repository already imports from, so this is EcoTaxa's anonymous policy, not a property of this
   deposit.

What is *not* blocked is the fetch itself: `POST /api/object_set/{project_id}/query` remains public
**once the id is known** — re-verified the same day against Tara Pacific HSN (project 11292, which
answered `total_ids: 256352`). The gap is one identifier, not an access wall.

## 5. What it would take to import it

One fact unblocks everything: **the EcoTaxa project id(s) holding these 11,079 vignettes**, from the
depositors, from a data paper when one appears, or from any EcoTaxa account that can see the
project. With it, the source is an ordinary member of the family this repository already supports —
the Tara Pacific route of [KI-29](../planktonzilla/planktonzilla_dataset/utils/KNOWN_ISSUES.md):

- walk the per-object manifest with `planktonzilla.dataset_import.ecotaxa_client`, then fetch one
  vignette per object from `/vault`, exactly as `tara_pacific_importer` does;
- **restrict to this deposit** by matching `obj.orig_id` against the table's `object_id` — the
  project may well hold more objects than the 11,079 published here;
- name class dirs from a committed `ecotaxa_taxon_id → class_dir` map rather than from the live
  `txo.display_name`, for the reason KI-29 records: EcoTaxa renames taxa in place, and a renamed
  folder silently repoints every `Raw_Labels` join key;
- carry the table itself as a sidecar — it is the only place the size measurements and the station
  metadata of §3.2 exist.

Two consequences to decide *before* that work, not during it:

- **The licence mix widens for the first time since KI-24.** `etalab-2.0` is a sixth set of terms:
  a new slug in `constants._LICENSE_DEEDS` and `DATASET_LICENSES`, a new value in the README licence
  column, and an entry in the published `LICENSE.md`. Licence Ouverte 2.0 is attribution-only, and
  its own text declares compatibility with CC BY 4.0, ODC-BY and OGL 2.0 — which is a statement
  about the licence, not legal advice about the composite.
- **Scale is not the argument for it.** 11,079 images is 0.06% of `planktonzilla-17M`. Its value is
  what the corpus is short of: annotated *freshwater* zooplankton, four seasons, with per-object
  size measurements and a 10.6 µm/px scale attached.

## 6. Traps a future import should already know about

Each was measured on the file itself; none is a reason to reject the source, and every one of them
is cheaper to read here than to rediscover.

**6.1 One taxon, two label strings.** `nauplii_Copepoda` (156) and `nauplii<Copepoda` (2) carry the
identical lineage. Mapping labels to taxonomy rows one-to-one would mint two rows for one taxon and
split 158 objects across two class dirs. Collapse them, and keep the more frequent spelling.

**6.2 The deposit's own date range disagrees with its data.** The Dataverse record declares
collection `2024-03` → `2024-12`; the `date` column runs **2024-02-13 → 2024-10-29**. Neither end
matches. Trust the column.

**6.3 The `object_id`'s second field is not a month.** It matches the sampling month for nine of the
twelve samples and not for the other three — all in Lake Geneva, where `LEM74_07_*` is 2024-05-13,
`LEM74_10_*` is 2024-07-01 and `LEM74_13_*` is 2024-09-03. It is a sample/scan counter. Read dates
from `date`; the id is a join key and nothing more.

**6.4 The lineages are EcoTaxa tree positions, not ranks.** `Maxillopoda` appears as the node above
`Copepoda` (EcoTaxa has since renamed that branch to `Multicrustacea` — the rename KI-29 records);
`Mesocyclops_leuckartii` and `Mixodiaptomus_laciniatus` hang from a lowercase `copepoda` node with
no family; `Cyclops_prealpinus` sits directly under `Cyclopidae` with no genus node, while
`Thermocyclops_crassus` has one. Depth ranges from 6 to 12 nodes. Reading a rank off a position is
wrong for **13 of the 19** lineages: seven skip the intervening ranks altogether — a species or
genus hanging straight off a family, off that lowercase `copepoda` node, or off a phylum
(`Asplanchna_priodonta` under `Rotifera`, `Dreissena_sp` under `Mollusca`) — and six end in a
qualifier leaf — `egg_sac`, `nauplii`, `part`, `part_cladocera`, `egg`, `ephippie` — which names a
specimen state, not a taxon.

**6.5 Three names need an authority decision before they become taxonomy rows.** Checked against the
GBIF backbone on 2026-09-18:

| Label | GBIF backbone says |
| --- | --- |
| `Cyclops_prealpinus` (2,697 — the second largest class) | *Cyclops prealpinus* Kiefer, 1939 is a **synonym** (`5719039`); the accepted usage is the subspecies *Cyclops abyssorum praealpinus* Kiefer, 1939 (`4326297`) — note `praealpinus` |
| `Mesocyclops_leuckartii` (1,013) | fuzzy-matches *Mesocyclops leuckarti* (Claus, 1857) (`4327382`); the deposit's spelling carries an extra `i` |
| `Leptodora_kindtii` (55) | fuzzy-matches *Leptodora kindti* (Focke, 1844) (`5179972`) |

The repository's own authority workflow
([`AUTHORITY_VERIFICATION.md`](../planktonzilla/planktonzilla_dataset/utils/AUTHORITY_VERIFICATION.md))
decides such cases; this is a head start on it, not a verdict. Expect blank `aphia_ID` throughout —
WoRMS is a marine register, and the FREPJ id-drafting record
([`FREPJ_DRAFTED_IDS.md`](../planktonzilla/planktonzilla_dataset/utils/FREPJ_DRAFTED_IDS.md))
already documents that a blank aphia is the *expected* outcome for a freshwater taxon, not a defect.

**6.6 Minor spelling inconsistencies.** `Diaphanosoma_sp.` carries a trailing dot that `Daphnia_sp`,
`Eubosmina_sp` and `Dreissena_sp` do not; `ephippie<Daphnia` uses the French *ephippie* rather than
the Latin *ephippium*.

## 7. Re-checking this record

Everything above is reproducible without an account, in under a minute:

```bash
# provenance, licence and file list
curl -s "https://entrepot.recherche.data.gouv.fr/api/datasets/:persistentId/?persistentId=doi:10.57745/9ZD7JW"
# the deposited workbook: 620,557 bytes, md5 b3b64ac23ec5a718b2827f8a754edc1b
curl -sL "https://entrepot.recherche.data.gouv.fr/api/access/datafile/708600?format=original" | md5sum
# the inventory of §3, from Dataverse's TSV ingest of sheet 1
curl -sL "https://entrepot.recherche.data.gouv.fr/api/access/datafile/708600" \
  | tail -n +3 | tr -d '"' | cut -f5 | sort | uniq -c | sort -rn
```

`tests/test_perialpine_zooscan_record.py` pins the tables above against each other and against the
README on every CI run, so a hand edit that breaks the arithmetic of this file fails there rather
than quietly becoming the record.
